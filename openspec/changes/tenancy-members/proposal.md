## Why

ADR-009 part 2, first of three changes (`tenancy-members` → `tenancy-shared-spaces` → `tenancy-document-shares`). `tenancy-foundation` gave every document a home space and mirrored it into Paperless, but there is still exactly one member, and the api reaches Paperless with one service token for every request — so a second person could only ever see everything or nothing. This change lets the household admin invite a second member, and makes every read and write of a member go through that member's own Paperless identity, so Paperless enforces the same isolation as aktenraum's policy.

New members join with an **interim password invite** (maintainer decision 2026-11-19): ADR-010 orders passkeys (its step 4) before more members; we invert that so sharing becomes usable sooner, and amend ADR-010 — when passkeys land, invite redemption switches to passkey enrolment and password members enrol a passkey on their next login, like the existing admin.

## What Changes

- **Invites**: the household admin creates a single-use invite link (valid 7 days), sees pending invites and can revoke them. The invitee opens the link, chooses a username and password, and is logged in as a new `member` with their own personal space, Paperless user and group. Redemption is rate-limited.
- **Members list** for the household admin in `/settings` ("Mitglieder"): username, role, joined.
- **Per-member Paperless tokens** (ADR-010 §8): aktenraum mints a Paperless API token for each member's Paperless user, stores it encrypted (AES-256-GCM, key `AKTENRAUM_SECRET_KEY`, new generated secret), and uses it for that member's requests. Tokens are disposable: a lost key or a rejected token is fixed by minting a new one.
- **Member-scoped reads and writes**: library (list, tag cloud, type chips), document detail / preview / download, review inbox, field edits / approve / reject / star / reprocess / delete, trash, upload and upload task tracking, live counts, import activity, Ask's structured search and duplicate candidates all run with the member's token. Paperless then only returns what that member may see; aktenraum's `PolicyService` stays the first check.
- **Service token stays** for the worker, internal routes, tenancy provisioning/migration, and the household admin's household-wide import activity (mail / consume-folder tasks belong to the service user).
- **Uploads** go to Paperless with the uploader's token, so the Paperless task and the new document belong to them from the first moment.
- **Configuration**: `AKTENRAUM_SECRET_KEY` added to `docker/.env.example` and generated by `scripts/bootstrap-secrets.sh`; the api refuses to start without it.
- **ADR-010 amendment**: interim password invites; passkey enrolment replaces them in ADR-010 step 4.

## Non-goals

- Shared spaces, moving documents, space picker on upload, library space column/filter (`tenancy-shared-spaces`).
- Per-document shares, "Mit mir geteilt", audit log (`tenancy-document-shares`).
- Removing or deactivating members, transferring a personal space (ADR-009 "member removal needs a defined flow").
- Per-member mailboxes and consume folders; mail and folder imports keep landing in the household admin's space.
- Passkeys, server-side sessions, persisted rate limits (ADR-010 step 4).

## Impact

- **API**: new tables `invites`, `member_paperless_tokens` (schema.ts + schema.sql + harness); `household/` module (invites, members, redemption — public routes added to the route inventory's allowlist); `tenancy/` (token minting + encryption, provisioning on redemption); `PaperlessGatewayProvider` gains a per-principal gateway; every service listed above takes the principal and asks for the member's gateway; `config/settings.ts` (`AKTENRAUM_SECRET_KEY`, fail-closed); upload uses the member token.
- **Web**: `/settings` "Mitglieder" section (admin), `/invite/[token]` page (bare layout, guest), settings visibility by role.
- **Scripts / config**: `docker/.env.example`, `scripts/bootstrap-secrets.sh`, upgrade runbook (new secret, recreate api).
- **Docs**: ADR-010 amendment, CLAUDE.md, session note.
- **Live data**: no migration; the existing admin's token is minted on first use.
