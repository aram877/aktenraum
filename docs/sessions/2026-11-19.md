## Follow-up: tenancy decision (ADR-009) + Paperless permission spike

### Focus / scope

Before rebuilding auth (passkeys, sessions, scopes, per-service credentials), decide the tenancy model, because a new job puts the maintainer in charge of auth and client integration and aktenraum should get the same treatment.

### What shipped

- **[ADR-009](../adr/009-tenancy-households-spaces.md)** — Household → Members → Spaces, one home space per document, plus explicit per-document shares (viewer/editor, optional expiry, never rule-based). One `PolicyService` decides access. RAG payload gains `space_id` + `shared_with`; few-shot, history hint and dedup are scoped to the home space so private content can't leak through prompts. Encryption mapping for the later cloud feature (per-space keys, per-document keys for shares).
- **Paperless spike** (`scripts/spikes/paperless-perm-spike.mjs`, `paperless-perm-spike-2.mjs`, throwaway e2e stack only). Result: Paperless 2.20 enforces per-user/group document permissions correctly across every list/filter/search endpoint we use (36/36), revocation is immediate, only owners can delete/move/re-share. So Paperless enforces as well (option b).
- **Trap found**: tags/types/correspondents are owned by their creator and invisible to other users. Decision: shared household vocabulary with `owner = null` (names visible to all members, per-user `document_count` verified). Accepted privacy trade-off recorded in the ADR.

### Read-only audit of the current auth coupling (input for the auth ADR)

- User auth is contained: one `AuthGuard`, `@CurrentUser()` read in two places. `AuthUser` carries `passwordHash` and has no scopes/session/client id; it becomes the `Principal`.
- Coupling points: `type-fields.controller.ts` `requireUserOrSecret` bypasses the guard; the CSRF bypass is keyed on the internal secret; four copies of the secret comparison; one `WEBHOOK_SECRET` shared by five callers; the SSE live-counts stream never re-checks its session.
- Single-user assumptions: no owner columns, one admin Paperless token, no owner in the Qdrant payload, ingest source detection relies on "ownerless task", unscoped live counts.

### Live install state (read-only)

498 tags, 22 types, 85 correspondents all owned by the Paperless admin; 257 documents (195 admin-owned, 62 ownerless). The migration steps are in ADR-009.

### Pick up next session

## Follow-up: the nightly backup never ran (catch-up scheduling + SPA warning)

### Focus / scope

`docker compose ps` showed the backup container unhealthy ("latest filesystem snapshot is 817h old"). Diagnose and fix.

### Repo state

- After `bf16a66` (ADR-009).
- Tests: 717 → 742 (core 176, api 249, worker 127, web 190). Lint, api + web typecheck and `nuxt generate` clean.

### Diagnosis

- None of the 20 restic snapshots was taken by cron. All came from setup or manual runs; the newest was 2026-10-16 (34 days old).
- The cron job was `0 2 * * *` UTC (03:00 local). The Windows event log shows the PC asleep from about midnight to 10:00. BusyBox crond doesn't catch up missed jobs, so on this host the job could never fire.
- The healthcheck reported it correctly, but only `docker compose ps` showed it.

### What shipped

- **Manual backup** right away (snapshots 2026-11-19 10:31; file tarball 240 MB vs. 112 MB on 2026-10-16).
- **Catch-up scheduling** (`docker/backup/`):
  - `backup-if-due.sh`, hourly at :07: backs up when the newest complete backup (the oldest of the three per-tag latest snapshots) is older than `BACKUP_INTERVAL_HOURS` (20), otherwise exits silently.
  - `start.sh` (new CMD): writes the status file, runs the catch-up check after `BACKUP_START_DELAY_SECONDS` (60), then `exec crond`.
  - `entrypoint.sh`:
    - an flock, so manual and scheduled runs can't overlap
    - an EXIT trap that writes `last-run` (time + exit code) and refreshes the status, also on `set -e` aborts
    - `restic check` keyed on "≥ 7 days since `last-check`" instead of Sundays
- **Backup health in the SPA**:
  - `healthcheck.sh` writes `backup-status.json` into the new `backup-status` volume (rw for backup, ro for the api).
  - `GET /api/health/backup` (session-guarded, `health/backup-status.ts`) returns `ok`/`stale`/`failing`/`unknown`. `failing` also covers a failed last run, an unreadable repository, and a status file older than 3 h.
  - The nav shows an amber "Backup veraltet" or red "Backup-Fehler" pill linking to the new **Settings → Backup** section (`components/settings/Backup.vue`).
- **Docs**: CLAUDE.md (known-gotcha row, backup section, test counts), configuration, api-reference, operations, first-time setup, architecture overview + diagram.

### Verification (live)

- crond is PID 1; the status file reaches the api; the route returns 401 without a session.
- A forced catch-up run (`BACKUP_INTERVAL_HOURS=0`) backed up, and a concurrent manual run skipped on the lock. The first run also performed the integrity check (no marker yet).
- A not-due run is silent. A simulated failure (wrong password, temporary status dir) records exit 1 with the real cause.
- The maintainer confirmed the Settings → Backup section in the browser ("Letztes vollständiges Backup vor weniger als einer Stunde").
- The real proof is the next wake-up: `docker compose logs backup` should show "Backup due … starting" within an hour.

### Diagnosed but not fixed (in this commit)

- With a wrong `RESTIC_PASSWORD`, the entrypoint logs "no restic repository at /repo", because every `restic snapshots` failure is treated as a missing repo. A fix is implemented and verified; it waits for confirmation and lands in its own commit.

- Desktop app (ADR-002): never assume the host is on at a fixed hour, for anything scheduled.
