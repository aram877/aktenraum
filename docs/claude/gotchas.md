# Known gotchas

> Moved out of CLAUDE.md to keep the always-loaded context small. Read this when working in this area.

## Known gotchas

| Issue                                                                                                       | Fix                                                                                                                                                                                             |
| ----------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **`AKTENRAUM_DATA_DIR` unset on Windows causes silent data loss** — `${HOME}` resolves differently from Git Bash vs PowerShell vs Task runner, so each `docker compose up` may write postgres to a new path and initialise a fresh empty DB, abandoning the old data (two incidents: May 20, May 23 2026) | Set `AKTENRAUM_DATA_DIR=D:/aktenraum` (or your chosen Windows path) in `docker/.env`. The `.env.example` now has this line uncommented with a warning. Never change it without migrating the data directory first. |
| Restic backup repo must exist before any snapshot. `task setup` performs the one-time `restic init`. The `backup` container's `entrypoint.sh` does **NOT** silently auto-init — it fails loudly when the repo is missing (set `BACKUP_AUTO_INIT=true` only for a deliberate new repo), so a drifted `AKTENRAUM_DATA_DIR` can't silently start a fresh empty backup history | First-time init: `task setup`. Verify recoverability with `task backup:verify` (non-destructive DR rehearsal) and integrity with `restic check` (see the Backup section). (NB: the historical "empty repo / silent no-op" was actually the cron-format bug in `docker/backup/crontab` — a `root` user-column that BusyBox crond couldn't run — fixed 2026-05-28, not a missing `restic init`.) |
| `docker compose restart` doesn't re-read env files                                                          | Use `docker compose up -d` to recreate the container                                                                                                                                            |
| Source changes don't take effect on restart                                                                 | `docker compose up -d --build auto-tagger` (or `task build`) to rebuild                                                                                                                         |
| Git Bash converts `/usr/local/bin/...` to Windows path in `docker exec`                                     | Prefix with `MSYS_NO_PATHCONV=1` and use `//usr/local/bin/...`                                                                                                                                  |
| Paperless `?name=` filter is silently ignored on `/api/tags/` (returns first page regardless)               | Use `?name__iexact=<name>`; keep the client-side equality re-check as defence in depth                                                                                                          |
| Paperless `data_type=string` custom fields have a hard 128-char limit                                       | Use `truncateForField` at the boundary; ellipsis on overflow. Use `data_type=longtext` (Paperless 2.x+) for fields that need more — extend the `LONGTEXT_FIELDS` set so truncation is skipped |
| Paperless `data_type=monetary` requires `<ISO><amount>` format                                              | Use `normalizeMonetary`                                                                                                                                                                         |
| Paperless `data_type=date` requires strict YYYY-MM-DD                                                       | Use `normalizeDate`                                                                                                                                                                             |
| Paperless's content-OCR date detector cannot be turned off via env var                                      | Rely on AI extracting `ai_issue_date` correctly so propagation overrides; or use `PAPERLESS_IGNORE_DATES` for known recurring bad dates                                                         |
| OCR fragments numbers ("28.02.24" → "2 8. 0 2.24")                                                          | `SYSTEM_PROMPT` explicitly tells the LLM to recognise this pattern; keep the rule when editing                                                                                                  |
| `ghcr.io/paperless-ngx/tika` requires auth                                                                  | Use `apache/tika` instead                                                                                                                                                                       |
| `python` vs `python3` differs across platforms (Git Bash has `python`, macOS has `python3`)                 | Scripts auto-detect with `command -v python3 \|\| command -v python`                                                                                                                            |
| Ollama model may return `---\n{...}` (YAML prefix) or integers in tag lists or `null` for empty list fields | Handled in `cleanJson` (`llm/ollamaBackend.ts`), `CoercedStrSchema`, `CoercedListSchema`                                                                                                        |
| Restic `--last` flag is deprecated                                                                          | Use `--latest <N>`                                                                                                                                                                              |
| Webhook + poller race-enqueue the same doc                                                                  | Worker re-checks lifecycle tags on dequeue, logs `skip_already_processed` if already processed                                                                                                  |
| Same content uploaded twice                                                                                 | Paperless dedups by SHA1 — duplicate is silently dropped, no double-processing                                                                                                                  |
| **CSRF middleware blocks browser requests with `Sec-Fetch-Site: cross-site`** on state-changing methods + `/preview` + `/download` | It decides from `Sec-Fetch-Site` alone; no credential exempts a request (the old `X-Aktenraum-Secret` exemption was removed 2026-11-19, ADR-003 amendment). Internal callers pass because Node's `fetch` sends no `Sec-Fetch-Site`. Internal identity lives in guards: `InternalGuard` (worker credential only — `/api/settings/active-*`, `/api/tenancy/*`) and `UserOrInternalGuard` (worker credential if an `Authorization` header is present, else the session — `PATCH /api/documents/{id}/type-fields`; any other bearer value is 401 `Invalid credential`, never a fallback to the cookie). No controller reads cookies or the `Authorization` header itself. |
| **A bearer header is judged alone** (personal-access-tokens) — a request with `Authorization` never falls back to the session cookie | `auth/bearer.ts` (`BearerAuthenticator`) is the only code that reads the header; the prefix picks the check: `akt_pat_` → token table, else the worker credential. `AuthGuard`: token only (anything else 401 `Invalid token`, even next to a valid cookie); `UserOrInternalGuard`: worker or token; `InternalGuard`: worker only (a token → 401 `Invalid credential`). Failed token attempts count on `token:ip:<address>` (10 / 15 min → 429 for every token from that address; behind `tailscale serve` the tailnet shares one bucket). A token principal has `sessionId: null` — a new route that needs the session must be `@SessionOnly()`. |
| `PaperlessClient` entity caches (tag id, custom field id, name maps) are TTL'd 5 min by default            | After out-of-band Paperless changes (`scripts/bootstrap-paperless.sh`, manual delete), call `client.invalidateCaches()` or wait one TTL; the gateway also auto-refreshes on unknown-field warnings |
| Auto-approve rule changes take up to 60s to take effect in the auto-tagger                                  | The auto-tagger fetches the rule set with a 60-second in-process TTL cache (`auto-approve-config.ts`). Saves in `/settings → Auto-Genehmigung` land in Postgres immediately but the next routing decision can use a cached older snapshot. On a SAVE-then-upload-immediately workflow this can mean the first doc still routes under the old rules. Workaround: wait one minute, or restart `auto-tagger` to force a cold fetch. Failures: rule store unreachable + populated cache → reuse cache + WARN; rule store unreachable + cold start → fail-closed (every doc → pending) until the next successful fetch. |
| `COOKIE_SECURE` defaults to `True`                                                                          | Localhost dev sets `COOKIE_SECURE=false` in `docker/.env` to allow login over plain http://localhost:8080; production HTTPS deploys leave it unset                                  |
| Login appears to succeed but every API call returns 401 — auth cookie set, never sent                       | Cause is `COOKIE_SECURE=true` (the default) combined with plain-HTTP access (typically `http://<lan-ip>:8080` from a non-host device). The browser refuses to send a `Secure` cookie over plain HTTP, so login looks like it works then bounces indefinitely. Fix: use the Tailscale MagicDNS HTTPS URL (`https://<host>.<tailnet>.ts.net/`) instead. Do NOT flip `COOKIE_SECURE=false` to "fix" this — that weakens security for no reason. See `docs/runbooks/tailscale-remote-access.md` failure-mode appendix. |
| `swapLifecycleTag` can raise `PaperlessConflictError` (HTTP 409) under heavy concurrency                  | Three-attempt verify-and-retry built in; if the third attempt still races, the SPA surfaces a "refresh and try again" message                                                                   |
| nginx `client_max_body_size 500m` caps total multipart upload size                                          | Per-file limit (`UPLOAD_MAX_FILE_BYTES`, 25 MB default) and file-count limit (`UPLOAD_MAX_FILES_PER_REQUEST`, 20) enforced server-side; MIME content-type allowlist rejects unknown formats     |
| Small LLMs (≤8B) drop `summary_de`, `reference_numbers`, `suggested_tags` despite the prompt rule           | Tagger has post-extraction fallbacks in `auto-tagger/src/synthesizers.ts`: `synthesizeSummaryDe` (deterministic German summary from struct fields) + `extractReferenceNumbersFromText` (regex sweep over OCR for Aktenzeichen/Rechnungsnr./Vertragsnr./Kundennr./Vorgangsnr./Bestellnr./Auftragsnr./Policennr./Steuernr.). Logs `summary_de_synthesized` / `reference_numbers_harvested` when they fire. `suggested_tags` has no synthesis fallback — risk of fabricating useless tags is higher than benefit |
| Approve action feels laggy (up to 30s before propagation)                                                   | The `POST /api/inbox/{id}/approve` handler fires a best-effort `POST /trigger/propagate` against auto-tagger (`AUTO_TAGGER_URL`, default `http://auto-tagger:8001`). The api sends `SVC_TOKEN_API`; both services load the same `docker/.env`. If the trigger returns 401 (`webhook_rejected reason=unknown_credential` in the worker log), check for `service_token_unset` and that the containers were recreated after the last `.env` edit (`task build` or `docker compose up -d`). Symptom: approve returns 200 but the doc takes up to 30s to flip from `ai-approved` → `ai-propagated`.                                                                                                                                                                                                                                                |
| **`DELETE /api/documents/{id}/` is a soft-delete, not hard-delete** — Paperless 2.x always moves to `/api/trash/` | The previous `PaperlessGateway.deleteDocument` docstring claimed "no soft-delete", which was wrong. Hard-delete only happens via `POST /api/trash/` with `action: "empty"` — the trash service does that AND `vectorStore.deleteByDocId` on the SPA's "Endgültig löschen" / "Papierkorb leeren" paths. Without an empty step, soft-deleted docs auto-purge after `PAPERLESS_EMPTY_TRASH_DELAY` days (default 30). A soft-deleted doc's Qdrant chunks stay in the index until the empty step, but carry `trashed: true` (indexed bool payload) and every `QdrantVectorStore.search` drops them (`must_not`, so chunks without the flag still match). `TrashFlagsService` (`trash/trash-flags.service.ts`) sets the flag after aktenraum's delete and the member-removal re-trash, clears it on restore (best effort, `trash_qdrant_flag_failed`), and reconciles against the full Paperless trash at api start + hourly (`trash_qdrant_reconcile_completed`) — that covers deletes/restores made in Paperless's own UI, with up to an hour's lag. Ask also drops any candidate Paperless no longer returns. |
| Auto-approve doesn't fire on a Rechnung you expected to skip review                                          | `docker compose logs auto-tagger \| grep routing_decision` and read the `reason=…` field on the matching `doc_id` line. Closed-enum values: `auto_approved` (both gates passed), `type_disabled` (rule.enabled=false for that type — flip the checkbox in `/settings → Auto-Genehmigung`), `confidence_below_min` (LLM gave the doc a low score relative to the per-type threshold — inspect `ai_confidence` + `ai_confidence_reason` in the inbox detail to see why, or lower the per-type Min. Konfidenz), `rules_unreachable_fail_closed` (aktenraum-api was unreachable at the auto-tagger's cold start — wait 60s or restart). Routing logic itself is correct and tested; the reason field tells you which gate blocked the doc. |
| Duplicate dismissal is sticky via `ai-duplicate-dismissed`                                                   | Clicking "Kein Duplikat" on a doc adds the `ai-duplicate-dismissed` aux tag in addition to removing `ai-duplicate`. The propagator's dedup helper (`findDuplicateIds` in `auto-tagger/src/propagate.ts`) short-circuits if the NEW doc carries the dismissed tag and filters out candidates carrying it from the comparison set — so a re-propagation against the same correspondent cluster doesn't re-flag the user's prior decision. To un-dismiss (re-enable detection on a doc), remove `ai-duplicate-dismissed` manually in Paperless's tag UI; the next propagation will treat it like a fresh doc again. |
| Qdrant tag payload only refreshes on star/unstar — NOT on `ai_suggested_tags` edits          | The RAG indexer (`indexDocument` in `auto-tagger/src/indexer.ts`) writes a doc's Qdrant payload (`tags`, `correspondent`, `doc_type`, `created_date`) exactly once, at first propagation. Editing "Vorgeschlagene Tags" on an already-`ai-propagated` doc in the Library review page only PATCHes the `ai_suggested_tags` custom field — it never touches Paperless's native `tags`, so it was never going to reach Qdrant either way; use "Erneut verarbeiten" if you want that edit to become real. The one native-tag-changing action that *is* kept fresh: starring/unstarring (`wichtig`) fires a best-effort `POST /trigger/reindex-metadata` (auto-tagger, mirrors `/trigger/propagate`) that refreshes just the Qdrant payload metadata via `QdrantVectorStore.updateMetadataByDocId` — no re-chunk, no re-embed. If a future feature adds a general native-tag editor to the Library page, wire it to the same trigger rather than reinventing it. |
| **The live LLM model is the DB setting, NOT `OLLAMA_MODEL`** — setting `OLLAMA_MODEL` while the api is up does nothing | `app_settings.llm_model` / `answer_llm_model` hold literal Ollama tags, edited in `/settings` (dropdown of pulled models, text input when Ollama is unreachable). The api reads them directly; the auto-tagger fetches `GET /api/settings/active-llm-model` (secret-gated) through `auto-tagger/src/active-model.ts` with a 60 s cache, reusing the last good value on a blip and falling back to `OLLAMA_MODEL` only on a cold failure (`active_llm_model_unreachable_using_env`). The Node worker skipped this lookup until 2026-10-01 (`harden-worker-pipeline`). Symptom of a bad value: `LLM-Extraktion fehlgeschlagen – model '<name>' not found (404)` → `ollama pull` it or pick another model in `/settings`. |
| **transformers.js caches models inside `node_modules`, not `HF_HOME`** — the Node reranker re-downloads ~545 MB on every image rebuild and can leave a truncated file | `@huggingface/transformers` ignores `HF_HOME`/`HUGGINGFACE_HUB_CACHE` unless `env.cacheDir` is set explicitly. Unset, the ONNX model lands in an image layer: it re-downloads on every `docker compose build`, and a rebuild that interrupts a download leaves a partial file that fails at load with `Protobuf parsing failed` / `ModelProto does not have a graph` — which reads like a corrupt model, not a caching bug. `packages/aktenraum-core/src/rag/reranker.ts` sets `env.cacheDir` from `TRANSFORMERS_CACHE`/`HUGGINGFACE_HUB_CACHE`/`HF_HOME`. Related: a short-lived process (e.g. the eval runner) can start the download and exit before it finishes, poisoning the cache — let the long-running API finish its prewarm first. |
| **Changing the embedding model/dimension requires a full re-index** — `ensure_collection()` only CREATES when missing, so it keeps a stale-dim Qdrant collection and new upserts/queries fail silently | Run `task rag:reembed`: it drops the `aktenraum_chunks` collection (from inside the auto-tagger container, no host curl) and runs `backfill --force`, which recreates it at the current `@aktenraum/core rag.DENSE_DIM` and re-embeds every document. Paperless docs are untouched — only the vector index is rebuilt; RAG/Ask is degraded until the backfill finishes. Also pull the new model first (`ollama pull <model>`) and set `EMBEDDING_MODEL` in `docker/.env`. |
| **Worker LLM calls are bounded and retried** | Structured Ollama calls time out after `LLM_TIMEOUT_SECONDS` (default 300) and request `num_ctx=OLLAMA_NUM_CTX` (default 24576 — Ollama's server default of 4–8k silently truncates the ~14k-char system prompt plus document text). A transient failure (connection refused, timeout, 429/5xx) leaves the document untagged and logs `extraction_deferred`; the 30 s poller retries it, and the third transient failure tags `ai-error`. The counter is in-memory and resets on restart. Streaming (`/ask`) has no timeout. |
| **RAG indexing safety** | The indexer embeds before deleting old chunks, so an Ollama outage during re-index never removes a document from search. `reindex-metadata` (star/unstar) only rewrites the Qdrant payload when chunks exist. The indexing queue is in-memory, so on every start the worker enqueues each `ai-propagated` document with zero chunks (`index_reconcile_completed`). A second startup step re-sets the chunk `space_id` where it disagrees with the home space (`reconcileChunkSpaces`, `index_space_reconcile_completed`); the worker often boots before aktenraum-api listens, so failed lookups are retried every 30 s (10 attempts, failed documents only) — one `index_space_reconcile_failed` line per attempt is normal right after a rebuild. Propagation skips any document that no longer carries `ai-approved` (`skip_not_approved`). |
| **The reranker must batch** — scoring all 50 candidates in one pass OOM-kills the api (exit 137, no log line) | `LocalReranker.rerank` scores in batches of `RERANK_BATCH_SIZE` (8) with `max_length` `RERANK_MAX_TOKENS` (512). Unbatched, bge-reranker-v2-m3 padded 50 pairs to the longest and blew past the 4 GB `AKTENRAUM_API_MEM_LIMIT` the moment an unfiltered RAG query returned many chunks — the container silently restarted mid-stream. Symptom: `/ask` returns only the `meta` event and `docker events --filter event=die` shows exit 137. Peak is now ~1.7 GB. |
| **nginx drops inherited `add_header`s in any location that declares its own** | The four security headers (CSP, `X-Frame-Options`, `nosniff`, `Referrer-Policy`) live in `docker/nginx/security-headers.conf` and are `include`d both at server level and inside `location = /index.html` (which adds `Cache-Control`). Before 2026-10-01 every SPA route was served without them. If you add a location with its own `add_header`, include the snippet there too — except the preview/download location, which deliberately sends `SAMEORIGIN` and no CSP so the SPA can frame PDFs. Verified with the strict CSP: all SPA pages render and the Chrome PDF viewer works in the iframe. |
| **Ollama reloads a model whenever `num_ctx` differs, and two big models don't share 24 GB** (fast-ask) | Ask took 20-57 s because extraction model, answer model and embedder evicted each other. Now: answer + embedder use Ollama's default `keep_alive` (5 min; `OLLAMA_KEEP_ALIVE=-1` pins them but holds ~20 GB VRAM, bad on a shared gaming GPU), `OLLAMA_ANSWER_NUM_CTX=12288` (24576 leaves no room for the embedder; 8192 is too tight for real prompts of ~8k tokens), embedder `num_ctx` fixed at `EMBED_NUM_CTX` (4096) in both worker and api. With the same model for extraction and answer keep both `num_ctx` values equal. The `/settings` hint warns when the two models differ. Remaining Ask latency is the CPU reranker (~0.3 s per chunk): lower `RERANK_CANDIDATES` or `RERANK_MAX_TOKENS`. `evals/golden-questions.yaml` is keyed to old doc ids and scores 0 hits — re-pin before using the eval. |
| **Healthchecks gate startup order** | redis, postgres, qdrant, paperless, aktenraum-api (`/api/health`), auto-tagger (`/health`) and nginx have healthchecks; nginx waits for a healthy api. Node images have no curl, so the checks run `node -e fetch(...)`. `docker compose ps` shows `(healthy)`. Memory caps: `PAPERLESS_MEM_LIMIT` (4g), `TIKA_MEM_LIMIT` (2g), `AKTENRAUM_API_MEM_LIMIT` (4g), `AUTO_TAGGER_MEM_LIMIT` (3g) — Docker Desktop's VM is ~8 GB on the dev Mac, so keep the sum sane. The worker's startup index reconcile retries every 30 s (10 attempts) because the worker can boot before Paperless answers. |
| **Backups were silently empty until 2026-10-01** — restic's Go file reads fail with `input/output error` on Docker Desktop bind mounts | Every snapshot from 2026-06-22 to 2026-09-30 contains the directory tree but no document files, and no DB dump: restic exited 3, `set -e` stopped the script before `pg_dump`. Plain C reads (`cat`, `tar`, Python) of the same files work; restic 0.16 and 0.18 both fail on `read(fd, buf, 524288)`. Fix: DB dumps run first, files go through GNU `tar` into `--stdin-from-command` (restic 0.18, alpine 3.22). Restore: `restic dump --tag filesystem latest aktenraum-files.tar \| tar -x -C "$AKTENRAUM_DATA_DIR"`. Verify with `task backup:verify` (now asserts original documents come back). A restic exit 3 is never benign. |
| **Starring did nothing once the install had more than 200 tags** — the api's tag name→id map only read page 1 | `PaperlessGateway.listNamed` fetched `page_size: 200` once; with 498 tags (2026-11-19) every name sorting after the 200th was invisible to the api. `swapLifecycleTag` couldn't resolve `wichtig`, `planTagSwap` skipped the unknown name, no PATCH was sent, and the star endpoint still answered 200. Library rows and the tag filter silently dropped the same tags. Fix: `listNamed` follows `next` across all pages (cap 50 × 200); `swapLifecycleTag` requires every tag to **add** to resolve (one cache refresh, then `PaperlessUnknownTagError` → 502) instead of silently writing nothing. The worker's `PaperlessClient.getEntityNameMap` already paginated. |
| **`pnpm install` fails on Linux x64: `onnxruntime-node` postinstall → `Failed to download the binaries: 404`** | transformers.js (reranker, via `@aktenraum/core`) pulls `onnxruntime-node`, whose postinstall downloads the optional CUDA/GPU binaries from a GitHub release on Linux x64 — that URL now 404s and kills the whole install. CI was red from 2026-10-23 to 2026-11-19 because of it; local image builds kept working only through Docker's layer cache, so a `--no-cache` rebuild (or a new machine) would have failed too. Fix: `ONNXRUNTIME_NODE_INSTALL_CUDA=skip` in the builder stage of `services/aktenraum-api/Dockerfile` + `services/auto-tagger/Dockerfile` and as workflow `env` in `ci.yml` (nginx already installs with `--ignore-scripts`). CPU binaries ship inside the npm package; nothing here uses CUDA. Set the same variable for a bare `pnpm install` on a Linux x64 host. |
| **The nightly backup never ran on a machine that sleeps at night** — the old `0 2 * * *` cron never fired | BusyBox crond does not catch up missed jobs. On 2026-11-19 the repo held 20 snapshots, none taken by cron, the newest 34 days old; the healthcheck said so, but only `docker compose ps` showed it. Fix: `docker/backup/backup-if-due.sh` runs hourly + at container start and backs up when the newest complete backup is > `BACKUP_INTERVAL_HOURS` (20) old; the weekly `restic check` keys on "7 days since the last check" instead of Sundays; backup health reaches the SPA via the `backup-status` volume → `GET /api/health/backup` → nav pill. Relevant for every desktop install (ADR-002): never assume the host is on at a fixed hour. |
| **`RESTIC_PASSWORD` was lost in the move to one `docker/.env`** | It only existed in the old `docker/backup.env`, so from late July the backup entrypoint died on `RESTIC_PASSWORD is required`. `bootstrap-secrets.sh` now carries secrets over from the old per-service env files, and refuses to generate a new restic password when `$AKTENRAUM_DATA_DIR/backup/restic-repo/config` exists (a new password cannot open the repo). |
| **Removing a member restarts the trash auto-purge clock of their trashed documents, and rolling the code back unlocks them** | Paperless hides trashed documents from `/documents/{id}/`, so the removal restores each one, re-mirrors it to the successor and trashes it again (`member_removal_documents.trashed` makes a resumed run finish the re-trash) — `PAPERLESS_EMPTY_TRASH_DELAY` starts over for those documents. A removal is a `member_removals` row that every member lookup filters on; reverting the code removes that filter, so before a rollback disable the removed member's login (`UPDATE users SET password_hash = 'disabled' …`, see ADR-009 "As built (`tenancy-member-removal`)"). A removal stuck at "wird abgeschlossen": `last_error` in `GET /api/household/removals`, retried every 5 min and at api start. |
| **Sessions are server-side rows; the cookie is only a lookup key** (auth-server-sessions, 2026-11-20) | The cookie holds 32 random bytes; `sessions.token_hash` stores their sha256 — never log or store the raw token. `__Host-aktenraum_session` with `COOKIE_SECURE=true`, `aktenraum_session` otherwise. Expiry 7 d idle / 30 d absolute, decided in SQL (the idle slide is a `CASE`, not `least()` — pg-mem lacks `least`, timestamp subtraction and `extract(epoch …)`). Logout, enrolment (the member's `password` sessions, `password_change`), member removal (all, `member_removed`) and the device list (`/settings → Konto → Geräte`, `GET/DELETE /api/auth/sessions[/:id]`, `POST /api/auth/sessions/revoke-others`) revoke rows; the live-counts stream re-checks its session every tick and ends with `session_ended`. Login is limited per username **and** per client address (10 failures / 15 min → 429 + `Retry-After`), invites per address, in `auth_rate_limit_events` — survives restarts. `trust proxy` = 1 makes `request.ip` the browser address behind nginx; behind `tailscale serve` all tailnet devices share one address. `auth_audit` records login/logout/revocation/password/invite events (180 days, no UI). The deploy that introduced this logged every device out once. |
| **Restricted sessions are deny-by-default** (auth-passkeys) — a new route is closed to password / recovery sessions unless marked `@AllowRestricted()` | A session started with a password or recovery code, or of a member with no active passkey, gets only `auth:enrol`; `authorize()` answers **403 `enrolment_required`** before checking scopes. Only `GET /auth/me` and `POST /auth/passkeys/register/begin|finish` are allowed (pinned in `test/route-inventory.test.ts`; `passkeys.routes.test.ts` walks every guarded route). The SPA's `auth` middleware and `useApi` send such a session to `/enrol`; the live-counts plugin doesn't open the stream for it. In api tests a password login is no longer a usable session — use `loginEnrolled` / the `household()` fixture. Personal access tokens are deny-by-default the same way: 403 **`session_required`** on every empty-scope route except `GET /auth/me` (`@AllowToken()`), every step-up route and every `@SessionOnly()` route (live-counts stream, `/auth/tokens*`) — pinned in `route-inventory.test.ts`, whose walk calls each with an all-scope token. |
| **Sensitive routes need a step-up within 5 minutes** — 403 `step_up_required` | `@RequireStepUp()` (list in ADR-010 "As built (`auth-passkeys`)", pinned by `test/route-inventory.test.ts`): trash empty / permanent delete, passkey rename/remove/add, recovery-code regeneration, invites, setup links, member removal, shared-space deletion and membership, LLM models, auto-approve. A passkey / setup / invite sign-in counts as one. The SPA's `useApi` runs the passkey dialog and repeats the request once (`withStepUp` in `utils/passkeys.ts`). Scripts that change settings need a stepped-up passkey session — `scripts/e2e-worker.sh` gets one through the setup-link CLI (`scripts/spikes/e2e-session.mjs`). Adding a new sensitive route: mark it and extend the pinned list. A personal access token never has a step-up: it gets 403 `session_required` there, not `step_up_required` (so a client doesn't try a passkey). |
| **A passkey only works on the host name it was created on** | `WEBAUTHN_RP_IDS` / `WEBAUTHN_ORIGINS` (default `localhost` / `http://localhost:8080` + the dev server); a ceremony from any other `Origin` is 400 before a challenge exists; IP addresses are refused at startup (browsers refuse passkeys there). Switching to the Tailscale name later = add it to both vars, `up -d aktenraum-api`, sign in there once (recovery code or setup link) and add a passkey. The login page shows a hint with the working addresses. |
| **Correlated subqueries in a drizzle `sql` template can silently compare a table with itself** — the live-counts stream reconnected ~140×/s (2026-11-22) | In a single-table `db.select().from(sessions)` drizzle renders `${sessions.memberId}` **unqualified** (`"member_id"`), so `EXISTS (SELECT 1 FROM member_removals WHERE ${memberRemovals.memberId} = ${sessions.memberId})` became `… = "member_id"`, which Postgres resolves to `member_removals.member_id` — one removal row (suzanna, 2026-11-20) made `SessionService.state()` call **every** session revoked. The stream answered `session_ended`, `/auth/me` (a different query) still said OK, the SPA restarted the stream at once. Fix: uncorrelated `${sessions.memberId} IN (SELECT "member_id" FROM "member_removals")` (same form as `tenancy/removed.ts`); regression test "keeps another member's stream open after someone else was removed"; the SPA now backs off after repeated `session_ended` (5 s doubling to 60 s, reset by any counts frame — `SESSION_ENDED_BACKOFF_MS` in `useLiveCounts.ts`). Rule: in `sql` templates never correlate on a column of the outer table — use `IN (SELECT …)` or alias explicitly. |

| **Non-root containers** | nginx runs `nginxinc/nginx-unprivileged` (uid 101, listens on **8080** inside; host port mapping unchanged), Qdrant runs `qdrant/qdrant:*-unprivileged` (uid 1000), both with `cap_drop: ALL`; api and worker were already `appuser` and also drop all caps; every built service has `no-new-privileges`. backup stays root (busybox crond, reads files owned by several uids).
