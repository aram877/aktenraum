# aktenraum-api notes (auth, tenancy, shares, library, inbox, upload)

> Moved out of CLAUDE.md to keep the always-loaded context small. Read this when working in this area.

## aktenraum-api notes

- NestJS app bootstrapped in `src/main.ts`, listening on port 8002. It runs as **ESM** — `@aktenraum/core` is ESM-only and a CJS build produced a dual-package hazard.
- **`applySchema()` runs before `NestFactory.create`.** It applies `src/db/schema.sql` (idempotent `CREATE TABLE IF NOT EXISTS`) in one transaction. Module init hooks query `users` and `auto_approve_rules`; without this a fresh database dies at boot. Note `src/db/0000_certain_guardian.sql` is drizzle-kit *introspection* output and is entirely commented out — a drift oracle, not a migration.
- Auth: server-side sessions (`auth/session.service.ts`, ADR-010 "As built (`auth-server-sessions`)"): an opaque random token in an httpOnly `SameSite=Lax` cookie (`__Host-` + `Secure` on HTTPS), only its sha256 stored in `sessions`. `AuthGuard` resolves it with one query and sets `sessionId` + `authTime` on the principal. `AuthRateLimiter` (Postgres) guards login and invites, `AuthAuditService` writes `auth_audit`, `AuthSweepService` prunes all three tables hourly. The SPA never reads the token. Tests: `src/auth/sessions.routes.test.ts`.
- **Passkeys** (`auth-passkeys`, ADR-010 "As built (`auth-passkeys`)"): `auth/webauthn.service.ts` (begin → single-use `webauthn_challenges` row, 5 min → finish claims it first, then `@simplewebauthn/server` verifies with UV required; `Origin` must be in `WEBAUTHN_ORIGINS`, RP ID = its host name), `auth/enrolment.service.ts` (first passkey → recovery codes → `password_retirements` → revoke `password` sessions → **new** session), `auth/recovery-codes.service.ts`, `auth/setup-links.ts` + `setup.controller.ts`, `auth/setup-link-cli.ts`, `auth/passkeys.controller.ts`, `CredentialAuditService` → `credential_audit`. Principal carries `authMethod`, `restricted`, `stepUpFresh` (computed in the one `SessionService.resolve` query). Tests drive every ceremony with `src/test/soft-authenticator.ts` (ES256, `none` attestation) via `src/test/passkey-helpers.ts` (`loginEnrolled`, `passkeyLogin`, `stepUp`, `joinWithInvite`); the `household()` fixture enrols everyone (pass `{ enrol: false }` for password members). Route tests: `src/auth/passkeys.routes.test.ts`.
- **Personal access tokens** (`personal-access-tokens`, ADR-010 "As built (`personal-access-tokens`)"): `auth/tokens.service.ts` (`create` / `list` / `revoke` / `revokeAllOfMember` / `resolve` — one query token ⋈ member ⋈ user, usage written at most once a minute, expiry and the 25-active cap in SQL), `auth/tokens.controller.ts` (`@SessionOnly()`, step-up on POST), `auth/bearer.ts` (`BearerAuthenticator`, used by all three guards). Token principal: `clientId: "pat"`, `authMethod: "token"`, `sessionId: null`, `token: {id, name}`, scopes = `TOKEN_SCOPES` ∩ role. Table `personal_access_tokens` (also in the pg-mem `SCHEMA_SQL` of `test/harness.ts`). Tests: `auth/tokens.service.test.ts`, `auth/tokens.routes.test.ts`, the token walk in `test/route-inventory.test.ts`.
- **Every member request reaches Paperless with the member's own token** (`tenancy-members`): services take the principal from their controller and call `MemberGateways.forPrincipal(principal)` (`tenancy/member-gateways.ts`) — a cached per-member `PaperlessGateway` whose token aktenraum mints on first use (superuser PATCHes the member's Paperless user with a random password, logs in once, discards it), stores sealed, and re-mints once on a 401 or an unreadable row. `PaperlessGatewayProvider.service()` (renamed from `require()`) is the superuser gateway and is used **only** for worker routes, tenancy provisioning/migration, the household admin's import activity and `type-fields.inferDocumentType`; a new member-facing call must not use it. Uploads go out as the member (task + document owned by them). Tests: `test/member-isolation.routes.test.ts` (two members, `FakeGateway.forToken` per-user views).
- **Household members** (`household/`): the household admin creates single-use invite links (7 days, SHA-256 of the token stored, `now() + interval` in SQL) in `/settings → Mitglieder`; an invitee joins at `/invite/<token>` with a username and a **passkey** (`POST /api/invites/:token/register/begin|finish`; the invite is claimed only after a verified ceremony) and becomes a passwordless (`password_hash = '!'`) `member` with recovery codes, their own personal space, Paperless user `ak-<id>`, group and token. The public invite routes are in the route-inventory allowlist; uniform 404; per-address `AuthRateLimiter` (Postgres); joining creates a session with `auth_method = invite` and a fresh step-up. **Member removal** (`household/member-removal.service.ts`, `tenancy-member-removal`): the admin removes a non-admin member with a successor (default: the admin) and a typed-username confirm — `GET /api/household/members/:id/removal-preview`, `POST /api/household/members/:id/remove`, `GET /api/household/removals`. A `member_removals` row is the lockout (every session revoked with `member_removed`, login answers like a wrong password, stored Paperless token deleted); everything member-facing filters with `tenancy/removed.ts` `notRemoved`. Phase `db` moves personal documents to the successor's personal space, makes the successor owner of owned shared spaces, drops other memberships and revokes received shares (audit `revoked` by the admin); phase `derived` deactivates the Paperless user (`is_active: false, groups: []`) and re-mirrors + re-sets the Qdrant space per document (`member_removal_documents.synced_at`). Failures answer 200 `completing`; `MemberRemovalService.syncAll` (startup + 5 min) finishes them. Uploads by a removed member follow the successor chain (`HomeSpaceService`). Test fixture: `household/member-removal.routes.test.ts`. `/auth/me` carries `household_role`; household settings sections render only for `admin`.
- **Shared spaces / "Akten"** (`spaces/`, `tenancy-shared-spaces`): any member creates a shared space and is its **only owner**; the owner adds household members (`GET /api/household/directory`) as `editor` or `viewer`, changes roles, removes them; non-owners leave. Paperless: writer group `space-<id>` + viewer group `space-<id>-view` (`space_paperless_groups`), shared documents `view=[writer,viewer]`, `change=[writer]`; membership changes only touch users' groups (`syncSpaceMembership`, `removeFromSpaceGroups`, then `MemberGateways.forget`), each undone with 502 when Paperless fails. `PolicyService` action `move` = owner only; placing into a space (upload, move in) = owner/editor (`SpacesService.canPlaceInto`). Move single (`POST /api/documents/:doc_id/move`) and bulk (`POST /api/spaces/:id/documents`, ≤ 200, per-document status) run DB → service-gateway mirror → Qdrant `setSpaceByDocId`, compensated. Upload `space_id` → `upload_task_spaces` → `HomeSpaceService` (falls back to personal when rights were revoked). Library rows carry `home_space`, `?space=` filter (`id__in`, chunked above 1,000 ids — Paperless 2.20 answers 414 around 16,000). Inbox + live-counts inbox skip viewer-space documents. Trash hard delete drops the `document_spaces` row. SPA: everything space-related is hidden until `household_member_count ≥ 2` (`useSpacesVisible`); `/akten` page, upload picker, library column/filter/bulk move, `components/spaces/MoveControl.vue` on both detail pages. Test fixture with three members: `src/test/household.ts`.
- **Document shares** (`shares/`, `tenancy-document-shares`): the home-space owner shares one document with one household member as `viewer` or `editor`, optional expiry (`document_shares`; history in `share_audit`). Routes `/api/documents/:doc_id/shares[/:member_id|/audit]` (`@DocumentAccess("share")`) and `/api/shares/with-me|by-me` (scope `shares:manage`). Grant/change/revoke: DB → `mirrorDocument` (service gateway; adds active recipients to `view.users`, editors to `change.users`) → Qdrant `setSpaceByDocId(doc, tenancy.qdrantSpaceFor(doc))`, undone with 502. "Active" is SQL-only (`tenancy/share-active.ts`); `SharesService.expireDue` sweeps every 5 min and, caller-scoped, at the start of library, with-me, inbox, live counts and Ask (Paperless + Qdrant first, then delete + audit `expired`). Moves keep `shared_with`. Recipients get `home_space: null` + `shared_by` (never the sharer's space name), no inbox entries (`TenancyService.notReviewableDocumentIds`), no corpus use. Access audit: `@ShareAccessKind("detail"|"preview"|"download")` on the read routes → `PolicyService.authorizeDocument` → `TenancyService.recordShareAccess` (≤ 1 per doc/member/kind/hour, best effort); Ask cites → `ask`. SPA: `components/shares/SharePanel.vue` on `/library/[id]` (home-space owner only), `/geteilt` (two tabs) + nav entry, "Geteilt von" in `HomeSpaceBadge` and library rows, detail pages hide state actions for share access and make fields read-only for share viewers (`canChangeState` / `canEditFields` in `utils/review-form.ts`). Tests: `src/shares/shares.routes.test.ts`, `apps/web/tests/nuxt/shares.spec.ts`.
- **Authorization (ADR-010 step 2, `principal-and-policy`)**: the auth guards (`AuthGuard`, `InternalGuard`, `UserOrInternalGuard`) build one `Principal` per request (`auth/principal.ts`: `member` with scopes from the household role, or the `worker` service with only `internal:settings-read` + `internal:type-fields-write`; no secrets) and then run `authorize`: the route's `@RequireScope(...)` (any-of; empty = any authenticated principal; **missing = 403**, and `test/route-inventory.test.ts` fails first) and, for `:doc_id` routes, `@DocumentAccess(read|write|edit-fields|delete|move|share)` checked by `PolicyService` (`policy/`), with a denial answered as **404** so existence doesn't leak. Controllers read the caller only via `@CurrentPrincipal()`. `MemberPrincipal` carries `memberId` (= `members.id`, what policy keys on), `userId` (= `users.id`, credential code only — password login, retirement check) and `householdId`; scopes come from the member's household role. `PolicyService` (tenancy-foundation §2): a member may act on a document when its `document_spaces` home space is one of the member's spaces and the space role allows it (`viewer` read, `editor` +write +edit-fields, `owner` +delete +move +share), or else an active share does (share `viewer` read, share `editor` read + edit-fields; a space role always wins); a document **without** a home space is household-admin-only (everything but `share`); the worker may only `edit-fields` (type fields) and read home spaces. `write` = state changes (approve, reject, inbox PATCH, reprocess, star, dismiss-duplicate); `edit-fields` = `PATCH /fields` + `PATCH /type-fields`. `PolicyService.accessOf` → `{via: space|share|admin, role}`, exposed as `access` on detail payloads.
- Bootstrap: on startup, if `users` is empty AND `BOOTSTRAP_USERNAME` + `BOOTSTRAP_PASSWORD` are set, one user is inserted. A reconciler inserts an `auto_approve_rules` row for any `DocumentType` missing one. Both idempotent across restarts.
- **Tenancy tables (ADR-009, `tenancy-foundation` in progress)**: `households`, `members` (one per user; role `admin`/`member`), `spaces` (`personal`/`shared`; one personal space per member), `space_members` (`owner`/`editor`/`viewer`), `document_spaces` (one home space per Paperless doc). `src/tenancy/reconcile.ts` fills them at startup (`onApplicationBootstrap`, after the bootstrap user exists): one household, first user = admin, a personal space per member; idempotent, never deletes. `members.paperless_user_id` / `spaces.paperless_group_id` link the Paperless user/group. Document detail responses (`/api/documents/{id}/detail`, `/api/inbox/{id}`) carry `home_space: {id, name, kind, owner}` (owner = the owning member's aktenraum username; null = unassigned), shown as the 📁 pill (`components/HomeSpaceBadge.vue`) in both detail headers (hidden below `sm:`). **Home space before extraction**: the worker calls `POST /api/tenancy/assign-home-space` (`InternalGuard`, worker scope `internal:tenancy-write`) first thing in `processDocument`; the api picks the uploader's personal space (`upload_task_members`, resolved via Paperless `/api/tasks/`, `paperless_doc_id = 0` = task made no document) or the household admin's, writes `document_spaces` and mirrors owner + group permissions into Paperless (`tenancy/paperless-mirror.ts`, users `ak-<members.id>`, groups `space-<spaces.id>`). 409 = a recent upload is still running → `home_space_pending`, retried without counting; other failures → `home_space_deferred`, `ai-error` ("Ablage-Zuordnung fehlgeschlagen") on the third. **Do not rebuild the live stack before the tenancy migration (§9)**: the first new document would provision the Paperless user/group and rewrite permissions outside the backup-gated run. `AuthGuard` resolves the member from the JWT's `users.id` via `TenancyService.resolveMember` (reconciles on demand for a user created after startup) and `PolicyService` decides by home space — see the Authorization bullet.
- DB: drizzle-orm over a node-postgres `Pool` (`src/db/db.module.ts`, injected as `DB` / `DB_POOL`).
- Schema: `src/db/schema.sql`, applied by `applySchema()` at startup (see above). `src/db/schema.ts` is the Drizzle model; `apply-schema.test.ts` fails if the two drift, so a new table must be added to both.
- The `aktenraum` Postgres database is created by `docker/postgres-init/01-create-aktenraum-db.sh` on a fresh `pgdata` volume. **For existing installs**, run once: `docker compose exec postgres psql -U paperless -c "CREATE DATABASE aktenraum OWNER paperless;"`

### Library (`/api/library/`)

- `GET /api/library/` — paginated list of non-pending documents. Server-side excludes `ai-pending` via `tags__id__none=<ai-pending-id>` so anything still under review never reaches the library.
- **Dokumenttypen chips**: `GET /api/library/types` returns `{name, count}` per native document type straight from Paperless's `document_count` (one request, uncached; counts the native FK, which is what the `document_type` filter uses, so chip counts match results). The sidebar shows them above the tags; a click toggles `?document_type=`. The type is the reliable category — every doc has exactly one — while AI tags are free-form and inconsistent; don't add a forced per-type tag, it would duplicate this. `ai-duplicate`, `ai-duplicate-dismissed` and `ai-index-error` are in the api's `INTERNAL_TAGS`, so they no longer leak into the tag cloud.
- **Status filter** (`?status=error|unprocessed|approved|done|rejected`, `paperless/status-tags.ts`): maps to tag queries — `error` = any of `ERROR_TAGS` (`ai-error`, `ai-propagation-error`, `ai-index-error`) via `tags__id__in`; `unprocessed` = none of the six lifecycle tags. The SPA's "Status" dropdown keeps it in `?status=`; its "In Prüfung" entry switches to the review tab instead. Under `status=error` the page offers **Alle fehlerhaften erneut verarbeiten** (`POST /api/documents/reprocess-failed`, server-side, ≤200 per call, sequential, per-doc failures reported).
- Query params: `document_type`, `correspondent`, `date_from`, `date_to`, `text`, `tags`, `page` (≥1), `page_size` (1..100), `ordering` (allowlist: `-created`, `created`, `-modified`, `modified`, `title`, `-title`). Cross-type amount filtering was retired with the generic `monetary_amount` field.
- Returns `LibraryItem` rows with `lifecycle_tags` so the SPA can render a small badge per tag (propagated / approved / rejected / error). Falls back to AI custom-field correspondent / doc_type when the native FK is unset.
- Money is no longer exposed at this layer — type-specific schemas carry it (Rechnung.gesamtbetrag, Mahnung.forderungsbetrag, Versicherung.jahrespraemie, etc.). The library and inbox detail pages surface them via `components/TypeFieldsSection.vue`.
- SPA route `/library` keeps filter state in URL search params (bookmarkable; back-button works); auto-applies form changes after a 400ms debounce; click row → `/library/$id`.
- `/library/$id` is the per-document review: PDF iframe on the left, editable form for the AI fields on the right (Speichern / Zurücksetzen / Erneut verarbeiten / Löschen / Herunterladen / ★). Backed by `GET /api/documents/{id}/detail` and `PATCH /api/documents/{id}/fields` — both reuse `aktenraum-api inbox.service` so they work on any doc, not just pending. Edits update only the AI fields; the propagator only runs on `ai-approved`, so to also rewrite the native Paperless fields the user clicks **Erneut verarbeiten** (which restarts the full pipeline). **Löschen** is a two-click confirm that moves the doc to the Papierkorb (`DELETE /api/documents/{id}`) and returns to `/library`. A doc tagged `ai-duplicate` shows `components/DuplicatePanel.vue` ("Mögliches Duplikat von #N" links from `/duplicate-candidates` + "Kein Duplikat"). Below the buttons, `components/TypeFieldsSection.vue` edits the type's `TYPE_FIELD_SCHEMA` fields (also on `/inbox/$id`); it PATCHes only changed keys to `/api/documents/{id}/type-fields`, sending `null` for an emptied field, which the API treats as "clear" (the worker never sends `null`, so a reprocess can't wipe a hand-typed value). There is no preview modal — Ask citations link to `/library/$id`.

### Upload + Reprocess (`/api/documents/upload`, `/api/documents/{id}/reprocess`)

- `POST /api/documents/upload` accepts `multipart/form-data` with one or many `files`; each is forwarded to Paperless's `/api/documents/post_document/`. Per-file failures are isolated — the response is `{results: [{filename, status, task_id, detail}]}`. Paperless dedupes by SHA1 so re-uploading the same content is a silent no-op.
- `POST /api/documents/{id}/reprocess` clears every lifecycle tag (`ai-pending`/`ai-approved`/`ai-rejected`/`ai-propagated`/`ai-propagation-error`/`ai-error` plus `ai-low-confidence`) so the document looks fresh to the auto-tagger; then best-effort pings `http://auto-tagger:8001/trigger/extract` for instant re-extraction. Without the ping (or if it fails) the auto-tagger's 30s poller picks the doc up regardless.
- Env: `AUTO_TAGGER_URL` (default `http://auto-tagger:8001`) and `SVC_TOKEN_API` (the api's service credential; empty → the worker refuses the ping and the poller takes over).
- SPA: `/upload` route with drag-and-drop + per-file progress; "Erneut verarbeiten" button on the library detail page with a two-click confirm. Reprocess success invalidates the `library` and `inbox` query caches so the UI snaps to the new state.

### Processing visibility (`/api/documents/in-flight`, `/task/{uuid}`, `/{id}/status`)

- `GET /api/documents/in-flight` returns `{count}` — number of docs carrying `ai-pending` or `ai-approved` (driven by `tags__id__in`). Empty lifecycle tags are intentionally excluded so legacy / non-AI docs don't keep the Nav badge stuck >0.
- `GET /api/documents/task/{uuid}` proxies Paperless's `/api/tasks/?task_id=…` and projects to `{task_id, status, doc_id, result}`. `doc_id` comes from `related_document` when present, falling back to a regex on the result string ("Success. New document id 19 created") so older Paperless versions still surface a usable id.
- `GET /api/documents/{id}/status` is a lightweight `{id, lifecycle_tags}` lookup used by the upload-page poller.
- `DocumentSummary` (returned by `/find` and the Ask `sources` / citations) carries `lifecycle_tags` so a single `ProcessingBadge` component renders the same status pill everywhere a doc card appears (Library rows, Find result cards, Ask citations). Empty list → "Wartet auf KI".
- SPA upload polling: after `/documents/upload` returns the Paperless task UUID, poll `/task/{uuid}` every 1.5s until SUCCESS, then poll `/{doc_id}/status` every 3s until a lifecycle tag appears or the 120s ceiling hits. The page renders one of: `Bereit → Wird hochgeladen → Paperless verarbeitet… → KI klassifiziert… → ✓ in der Inbox / ✓ in der Bibliothek / ✗ Fehler` per file.
- Nav shows a red **"N Fehler"** pill (live-counts `errors`, fallback poll of `/library/?status=error&page_size=1`) linking to `/library?status=error`.
- Nav shows a global "N in Bearbeitung" pill (in-flight count minus inbox count, so it represents docs the _auto-tagger_ is processing right now — pending docs already get the Inbox badge). Values come from the live-counts SSE stream, with a 30s Vue Query poll as fallback.

### Document proxy (`/api/documents/{id}/{preview,download}`)

- `GET /api/documents/{id}/preview` streams the inline PDF preview (`Content-Type: application/pdf`, `Cache-Control: private, max-age=300`). Embedded as an iframe on the library and inbox detail pages.
- `GET /api/documents/{id}/download` streams the original file with the upstream `Content-Disposition` forwarded so the browser saves with the right filename.
- Both proxy through `aktenraum-api` so the Paperless API token stays server-side. nginx's `proxy_read_timeout` is bumped to 300s in `docker/nginx/nginx.conf` because LLM-backed endpoints can take ~30s on bigger local models.

Without `PAPERLESS_API_TOKEN` set, `/api/ai/*` and `/api/documents/*` respond 503 while `/api/health` and `/api/auth/*` stay green. Same for missing `ANTHROPIC_API_KEY` when `LLM_BACKEND=anthropic`.

### Inbox review (`/api/inbox/*`)

- `GET /api/inbox/` paginated list of `ai-pending` documents (oldest-first); `GET /api/inbox/{id}` full review payload (12 ai\_\* fields + content excerpt + tags); `PATCH /api/inbox/{id}` partial field update; `POST /api/inbox/{id}/approve` (optional patch body, then swaps `ai-pending` → `ai-approved`); `POST /api/inbox/{id}/reject`; `GET /api/inbox/{id}/preview` streams the PDF with `Content-Type: application/pdf`, `Cache-Control: private, max-age=300`. All auth-gated.
- Lifecycle-tag swap is a single `tags=[…]` PATCH planned by `planTagSwap` (pure helper). Idempotent re-approve / re-reject is a no-op.
- **Paperless `custom_fields` PATCH is full-array replace**, not partial upsert — sending only `{ai_correspondent: …}` would wipe the other 11 fields. The gateway's `patchDocumentCustomFields` reads the existing array, merges the requested updates by field id (`mergeCustomFields`), then writes back. Same gotcha class as the silent `?name=` and `?correspondent=` filters.
- Field-update normalisation reuses the normalisers in `@aktenraum/core` — date fields go strict ISO, monetary becomes `<ISO><amount>`, strings get truncated to 128 chars. Server-side at the boundary; client cannot bypass.
- SPA: the review queue lives at `/library?tab=review` (`apps/web/app/components/library/ReviewTab.vue`, rendered by `pages/library/index.vue`). There is no bare `/inbox` route — it falls through to the `[...slug].vue` not-found page. The list supports **multi-select bulk approve**: per-row checkboxes + a header "select all" checkbox + a sticky dark action bar that runs `useBulkApprove` (parallel POSTs against `/api/inbox/{id}/approve`) and reports `N genehmigt · M fehlgeschlagen`. **Pagination is load-more, not page-jump**: the tab uses `useInboxListInfinite` (TanStack `useInfiniteQuery`, pageSize=50) so multi-select spans loaded chunks naturally — review is a triage flow, not random-access browsing. "Mehr anzeigen" button below the table renders while `hasNextPage`; counter shows `N von M geladen`. Bulk-approve `invalidateQueries({queryKey: INBOX_KEY})` invalidates all loaded pages, triggering a sequential refetch (acceptable: refetch only fires once per bulk operation, and the refetched state is usually much smaller because most loaded docs just got approved). Per-doc detail page is `/inbox/$id` — two-pane review (PDF iframe via the proxy + editable form), keyboard shortcuts `a` Approve / `r` Reject / `j`,`k` next/prev / `Esc` back. Auto-advance to the next pending doc on action; back-out / Escape navigate directly to `/library?tab=review` (no redirect hop).

`prompt.ts` disables `max-len` for the file on purpose: `SYSTEM_PROMPT` is a long German-text block where wrapping damages the prompt as content. Its exact length (14,118 chars) is asserted by a test, so an accidental edit fails CI rather than silently changing extraction behaviour on every document.
